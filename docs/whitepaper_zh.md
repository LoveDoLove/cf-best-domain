## 一、 执行摘要与项目愿景

Cloudflare 依托其遍布全球的边界网关协议（BGP）Anycast 广播网络，为数千万互联网资产提供安全防护与内容分发加速。在理想的网络拓扑下，Anycast 能够将终端请求自动路由至物理距离或网络距离最近的边缘节点（Point of Presence, PoP），从而实现极低的时延与高可用性。

然而，在跨国、跨运营商的复杂公网互联环境下——尤其是中国大陆四大基础电信运营商（中国电信、中国联通、中国移动、教育网）访问海外边缘网络时——默认的 BGP Anycast 广播调度机制往往会出现严重的路由劣化。受制于运营商商业对等互联协议（Peering Policy）、跨境光缆出口拥塞以及非对称路由策略，大陆用户的访问流量经常被错误引导至地理位置极为遥远或处于拥堵状态的边缘节点（例如，东亚地区的流量被强行路由至美国西海岸圣何塞或洛杉矶节点），导致往返时延（RTT）飙升至 300ms 以上，并伴随严重的 TCP 重传与丢包。

**cf-best-domain** 正是为彻底解决这一结构性痛点而生。

本项目的核心愿景是**“边缘性能加速的平民化”**：让每一位独立开发者、站长、中小团队及开源项目，都无需负担高昂的商业化费用，即可全自动、零维护、零成本地将访问流量智能调度到本地区实时最优、延迟最低的 Cloudflare Anycast 节点上。

## 二、 问题背景：Anycast 路由困境

### 2.1 BGP Anycast 的运行机制
在标准 Anycast 架构中，分布于全球数百个数据中心的边缘路由器均使用同一组 IP 地址前缀向全球公网宣告 BGP 路由。公网上的各级自治系统（ASN）主要依据以下规则进行路径优选：
1. BGP AS-Path 路径跳数；
2. 中转运营商（Transit Provider）的局部商业偏好（Local Preference）；
3. 运营商间的结算互联政策（Settlement-Free Peering）。

### 2.2 路由劣化现象与成因
BGP 路由协议在本质上对**实时网络质量完全盲目**：它无法主动感知端到端链路的时延、抖动、丢包率或边缘服务器的实时负载情况。这直接导致了以下常见问题：
- **非对称路由与环流**：去程数据包经由拥堵的跨洋海缆，回程数据包经由亚太骨干网，导致 TCP 拥塞窗口剧烈收缩，网页首屏加载极慢；
- **跨网结算调度异常**：国内不同运营商在晚高峰时段对国际出口带宽进行流量整形，原本低延迟的直连线路（如香港、东京、新加坡、首尔等 PoP）被绕开，大量普通访问被甩向北美大区；
- **高昂的企业级准入门槛**：虽然 Cloudflare 官方提供了 China Network 及自定义流量调度（Traffic Steering）方案，但此类企业级（Enterprise）产品每月成本高达数千美元，使得个人开发者与中小团队望尘莫及。

### 2.3 优选 IP（Optimal IP）技术路径
由于 Cloudflare 的全网 Anycast IP 段在全球多数节点均可完成握手与反向代理，网络测速平台（如 wetest.vip 等）通过在国内各大骨干网探针发起高频、全维度的测速探测，能够实时筛选出当前对国内各运营商延迟最低、丢包率最低、链路最干净的可用 Anycast IPv4 节点。

将这些动态优选出的 IP 地址直接作为域名 A 记录写入权威 DNS，即可跳过低效的默认 BGP 路由选举，强行让终端流量直达性能最佳的边缘机房。

## 三、 核心设计理念

`cf-best-domain` 的架构演进始终恪守四项核心工程原则：

### 3.1 极致轻量与极简主义 (Radical Simplicity / KISS)
代码库摒弃一切非必要的复杂度：
- 严禁引入容易因反爬或页面改版而崩溃的多来源网页爬虫；
- 拒绝引入重量级外部数据库（PostgreSQL/Redis/SQLite），不产生额外存储负荷；
- 无需长期运行驻留的后台守护进程（Daemon）。

### 3.2 零运维与无服务器架构 (100% Serverless & Zero Cost)
从定时探测、数据验证，到 Git 提交与 Cloudflare DNS 全量同步，整个生命周期完全依托 GitHub Actions 免费提供的托管容器调度，实现 0 VPS 租金、0 电费、0 硬件折旧。

### 3.3 防御式自动化与熔断机制 (Defensive Automation)
自动化调用具有破坏性的 DNS 接口（批量删除并重建 A 记录）蕴含着极高的业务风险。上游接口的偶发故障绝不能引发线上域名的解析灾难：
- 内建基于文件状态的**非空熔断器**，空数据自动中断；
- 采用带租约的安全推送机制（`--force-with-lease`），杜绝意外覆盖开发者手动提交的历史。

### 3.4 声明式中间解耦 (Decoupled Intermediate Artifacts)
IP 采集端与 DNS 同步端通过仓库根目录下的标准化纯文本文件 `ip.txt` 完全解耦。这一设计使得每一轮 IP 的演进变化都在 Git 历史中留存清晰的可审计 Diff，且支持随时在本地脱机调试。

## 四、 整体系统架构与数据拓扑

`cf-best-domain` 采用两阶段串行数据流水线，由 GitHub Actions 定时任务统一编排：

```
  +-----------------------------------------------------------------------+
  |                          第一阶段：采集流水线                          |
  |                                                                       |
  |  +--------------------+     HTTPS GET      +-----------------------+  |
  |  |   wetest.vip API   | =================> |  fetch_wetest_ips.py  |  |
  |  +--------------------+    (内建 3 次重试)   +-----------------------+  |
  |                                                        |              |
  |                                                        v              |
  |                                            +-----------------------+  |
  |                                            |    ip.txt (中间产物)   |  |
  |                                            +-----------------------+  |
  |                                                        |              |
  |                                                        v              |
  |                                            +-----------------------+  |
  |                                            |  Commit 智能压缩引擎   |  |
  |                                            | (Soft Reset + Lease)  |  |
  +--------------------------------------------------------|--------------+
                                                           |
                                                           v
  +-----------------------------------------------------------------------+
  |                          第二阶段：DNS 智能同步                        |
  |                                                                       |
  |  +-----------------------+     校验通过     +-----------------------+  |
  |  |   ip.txt 非空熔断保护   | =============> |update_cloudflare_dns.py| |
  |  +-----------------------+                 +-----------------------+  |
  |              | 异常/为空 (立即熔断)                    |              |
  |              v                                         v              |
  |        [终止流程 Exit 1]                    +-----------------------+  |
  |                                            |  Cloudflare REST v4   |  |
  |                                            | - 自动查询目标 Zone ID |  |
  |                                            | - 循环清理废弃 A 记录   |  |
  |                                            | - 批量创建全新 A 记录   |  |
  |                                            +-----------------------+  |
  |                                                        |              |
  |                                                        v              |
  |                                            +-----------------------+  |
  |                                            | 极速访问的终端用户网络  |  |
  +-----------------------------------------------------------------------+
```

### 4.1 核心组件职责

1. **IP 采集引擎 (`fetch_wetest_ips.py`)**：
   - 携带鉴权 Key 与 `type=v4` 参数请求指定数据源；
   - 递归遍历任意层级的返回 JSON 载荷；
   - 严格进行 IPv4 规范性验证并完成唯一性去重；
   - 输出标准化格式的 `ip.txt`。

2. **状态解耦桥梁 (`ip.txt`)**：
   - 纯文本文件，每行一个合法 IPv4 地址；
   - 纳入 Git 版本控制，提供完整的 IP 演化审计链路。

3. **DNS 同步引擎 (`update_cloudflare_dns.py`)**：
   - 基于 Token 权限查询目标主域名对应的 Zone ID 与顶级域名；
   - 遍历子域名映射配置表（`subdomain_ip_mapping`）；
   - 循环检索并全量删除指定子域名（如 `api.domain.com`）现存的所有旧 A 记录；
   - 将 `ip.txt` 中的优选节点以 `TTL=1`（自动）及 `proxied=false`（直连）模式批量写入。

4. **自动化工作流编排 (`.github/workflows/`)**：
   - `collect_ip_list.yml`：每 30 分钟周期运行，执行采集、Commit 智能压缩与推送；
   - `update_cloudflare_dns.yml`：每 30 分钟周期运行，校验密钥、执行采集、触发非空熔断检查、完成 DNS 最终一致性更新；
   - `cleanup-failed-runs.yml` / `cleanup-all-runs.yml`：清理 GitHub Actions 执行历史日志。

## 五、 关键技术细节与实现机制

### 5.1 任意层级 JSON 递归提取与 IPv4 校验
上游 API 的返回格式在长期演化中可能变更结构（如调整字段包裹层级、增加运营商分类嵌套等）。为了杜绝模式脆弱性（Schema Brittleness），`fetch_wetest_ips.py` 实现了任意复杂对象的递归生成器遍历：

```python
def walk_values(obj: Any) -> Iterable[str]:
    if isinstance(obj, dict):
        for value in obj.values():
            yield from walk_values(value)
    elif isinstance(obj, list):
        for item in obj:
            yield from walk_values(item)
    elif isinstance(obj, str):
        yield obj
```

提取出的所有字符串均通过 Python 标准库 `ipaddress.ip_address(value).version == 4` 进行严格校验，非合规字符串与非 IPv4 数据被安全静默丢弃。

### 5.2 跨国网络瞬态抖动吸收算法
GitHub Actions 云端 Runner（部署于微软 Azure 全球数据中心）在访问国内边缘接口时，偶发遭遇跨境 TCP 连接握手超时（ConnectTimeout）。

脚本内部设置了三级容错机制：
- 单次请求 Timeout 设置为 20 秒；
- 遭遇 `requests.RequestException` 时最多自动重试 3 次；
- 重试间隔 5 秒退避；
- 实测该机制可吸收 99.9% 的瞬态网络波动，避免工作流误报失败。

### 5.3 智能 Commit 压缩状态机
若每 30 分钟产生一次独立 Git 提交，仓库每月将累积近 1,500 条自动提交，导致 Commit 历史极度臃肿。

`collect_ip_list.yml` 设计了一套轻量级提交状态机：
1. 检测到 `ip.txt` 产生差异时，读取最新一条提交的作者与 Message；
2. 若上一次提交系 `github-actions[bot]` 生成的 `Automatic update`：
   - 执行 `git reset --soft HEAD~1`，将上一次自动提交撤回至暂存区；
   - 将全新变动与上一次变动合并后，重新以 `Automatic update` 提交；
   - 使用 `git push --force-with-lease origin HEAD:<branch>` 实施原子化安全覆盖。
3. 若上一次提交系人工开发者的代码提交或 PR 合并：
   - 绝不执行回滚，以普通提交模式追加一次提交，确保开发者历史不被篡改。

### 5.4 非空安全熔断器 (Circuit Breaker)
在 DNS 体系中，删除旧记录操作是不可逆的。一旦上游 API 临时宕机导致拉取到的 IP 列表为空，若贸然执行删除，域名解析将被瞬间清空，导致服务彻底瘫痪。

工作流在执行 DNS 更新脚本之前，内嵌了严格的 POSIX 文件非空判定：

```bash
if [ ! -s ip.txt ]; then
  echo "ip.txt is empty; aborting Cloudflare DNS update"
  exit 1
fi
```

当文件大小为 0 时立即抛出 `exit 1`，强行终止流水线，成功拦截对线上 DNS 的误伤。

## 六、 安全架构与威胁模型分析

本项目严格执行云原生最小权限安全规范：

### 6.1 最小权限原则 (PoLP)
- **Token 权限收敛**：强烈要求在 Cloudflare 控制台创建 API Token 时，仅勾选 `区域 (Zone) - DNS - 编辑` 权限，并将作用域严格圈定在目标主域名内；
- **杜绝全局凭据**：全面废除并禁止使用权限过大的 Cloudflare Global API Key。

### 6.2 零凭据存储与日志脱敏
- 仓库代码、历史提交及生成的中间产物中严禁出现任何明文密码与密钥；
- 密钥由 GitHub Secrets 统一加密托管，仅在容器运行时通过环境变量挂载，GitHub Actions 自动执行日志流脱敏处理。

### 6.3 极简软件供应链安全
- 仅依赖官方标准库与经过全球开发者长期验证的 `requests` 库；
- 零多层嵌套第三方间接依赖（Zero Transitive Dependencies），彻底阻断了常见的 NPM / PyPI 恶意供应链投毒攻击面。

## 八、 未来演进规划与发展路线图

`cf-best-domain` 2.0 虽已高度稳定，但在未来版本中仍将按以下规划持续演进：

### 8.1 声明式配置驱动 (Declarative Configuration)
- **目标**：将子域名映射与运行参数从 Python 源码中完全解耦，引入独立的 `config.yaml` 或 `config.json`。
- **价值**：用户无需阅读或改动任何 Python 脚本，仅需修改配置文件即可扩展多个二级子域名甚至根域名（`@`）。

### 8.2 多云 DNS 服务商适配 (Multi-Provider Support)
- **目标**：抽象 DNS 接口适配层，支持接入更多云服务商的权威 DNS 服务。
- **支持规划**：阿里云 DNS (Alibaba Cloud)、腾讯云 DNSPod、华为云 DNS、AWS Route 53 及自建 PowerDNS。

### 8.3 多源融合与分布式健康测速
- **目标**：支持接入多个备用测速接口（如 hostmonit、社区测速探针群），在上游主接口波动时自动平滑故障转移；
- **健康共识机制**：对多个测速源的重合 IP 进行加权评分，优先挑选各探针均判定优质的超级节点。

### 8.4 事件驱动告警通知 (ChatOps Integration)
- **目标**：提供开箱即用的 Webhook 通知适配器。
- **通知渠道**：支持 Telegram Bot、Discord Webhook、企业微信、飞书、Slack，在非空熔断触发或大版本 IP 切换时向管理员即时发送告警卡片。

## 九、 总结

`cf-best-domain` 的实践充分证明：通过巧妙结合云原生无服务器（Serverless）工作流、严谨的防御式自动化脚本与智能 Git 历史压缩机制，无需昂贵的企业级网络套餐与高昂的服务器维护成本，每一位普通开发者都能以零成本构建出生产级的高可用、低时延边缘网络加速调度体系。
